prepare.py: the fixed data, tokenizer, and metric

Conclusion

prepare.py runs once to download text data and train a tokenizer (the part that splits text into tokens). After that, train.py imports three fixed tools from it on every run: the tokenizer, a dataloader, and evaluate_bpb. The agent may not edit it, because it defines the test. Every experiment is scored on the same validation text (shard 6542), the same 20,971,520 evaluation tokens, and the same bits-per-byte formula.

This page assumes the file split from the main page: the human edits program.md, the agent edits train.py, and prepare.py stays fixed.

What does prepare.py do once, and what does it give train.py on every run?

The file has two jobs, shown as the two panels of Figure 1. The top panel runs once, when you type uv run prepare.py. It writes its results to ~/.cache/autoresearch/. The bottom panel is the code that train.py imports and runs on every experiment.

The constants at the top of the file are the other half of the fixed test. train.py imports MAX_SEQ_LEN and TIME_BUDGET directly (its line 26).

Which data does it download, and why is one validation shard pinned?

It downloads parquet files (a column-based data file format) from the Hugging Face dataset karpathy/climbmix-400b-shuffle. Each file is one shard. By default it takes shards 0–9 for training (--num-shards 10). It always adds shard 6542, the last one, for validation (lines 91–97). Figure 2 shows which code reads which shard.

Three places in the code keep the validation shard apart. text_iterator leaves it out when it trains the tokenizer (line 127). The training dataloader removes it from its file list (lines 259–261). The validation dataloader reads only that file (line 263). If the model had trained on the validation text, a lower val_bpb could mean memorized text, not a better model. Because the shard number is a constant, every experiment, on every machine, is scored on the same text.

Source: prepare.py lines 41–44 (BASE_URL, VAL_SHARD), 91–97, 125–127, 254–263, 373 (--num-shards default 10).

How does the dataloader fill every row without padding?

It packs whole documents into each row, choosing the largest one that still fits. The docstring calls this “best-fit packing” with “100% utilization (no padding)”. Each row holds 2,049 tokens: the targets are the inputs shifted by one token, so 2,048 inputs need one extra token (lines 334–335). Every document starts with the BOS (beginning-of-sequence) token, so every row starts at the beginning of a document.

In Figure 3, the row has 449 positions left after documents A and B. Lines 317–321 search the buffer of about 1,000 documents for the largest one with at most 449 tokens, here document D. When no document fits the last 49 positions, lines 329–331 take the shortest document and keep only its first 49 tokens.

# prepare.py lines 323–332
                if best_idx >= 0:
                    doc = doc_buffer.pop(best_idx)
                    row_buffer[row_idx, pos:pos + len(doc)] = torch.tensor(doc, dtype=torch.long)
                    pos += len(doc)
                else:
                    # No doc fits — crop shortest to fill remaining
                    shortest_idx = min(range(len(doc_buffer)), key=lambda i: len(doc_buffer[i]))
                    doc = doc_buffer.pop(shortest_idx)
                    row_buffer[row_idx, pos:pos + remaining] = torch.tensor(doc[:remaining], dtype=torch.long)
                    pos += remaining

Line 330 removes the document from the buffer, so the cropped tail is never used. Choosing the largest fit first leaves small gaps, and a small gap means a short crop. This matters inside a fixed time budget: an empty position would cost GPU time and teach nothing.

How does evaluate_bpb turn loss into bits per byte?

It adds up the model's loss over all validation tokens and divides by the number of bytes those tokens stand for. The loss of one token is the cross-entropy, measured in nats (the natural-log unit; 1 nat = 1 / ln 2 ≈ 1.443 bits). Line 365 converts the sum to bits per byte:

val_bpb = Σ lossnats ÷ (ln 2 × Σ bytes)

A worked example with three illustrative tokens:

Target tokenBytesLoss (nats)
"The"31.2
" cat"42.9
" sat"41.4
Sum115.5

val_bpb = 5.5 ÷ (0.693 × 11) ≈ 0.72. The upstream baseline, 0.9979, means the model needs about 1 bit to encode each byte of validation text. Plain UTF-8 text uses 8 bits per byte.

# prepare.py lines 357–365
    for _ in range(steps):
        x, y, _ = next(val_loader)
        loss_flat = model(x, y, reduction='none').view(-1)
        y_flat = y.view(-1)
        nbytes = token_bytes[y_flat]
        mask = nbytes > 0
        total_nats += (loss_flat * mask).sum().item()
        total_bytes += nbytes.sum().item()
    return total_nats / (math.log(2) * total_bytes)

Line 361 looks up each target's byte length in the table that train_tokenizer saved. Special tokens have length 0, and line 362 removes them from the loss sum. With the default batch of 128 rows, the loop runs 20,971,520 ÷ (128 × 2,048) = 80 times.

The docstring calls bits per byte “vocab size-independent”. A tokenizer with a larger vocabulary makes longer tokens, so the loss per token grows even when the model is equally good. The number of bytes in the validation text does not depend on the tokenizer.

Inference

Within one autoresearch run, VOCAB_SIZE is fixed, so every experiment already uses the same tokenizer. The byte normalization matters most when a human changes VOCAB_SIZE, as the README suggests for small computers, or compares results with a fork that uses another tokenizer.
