autoresearch: an AI agent that runs LLM experiments overnight

Conclusion

autoresearch lets an AI coding agent run small LLM (large language model) training experiments without a human. The agent changes only train.py, trains for a fixed 5 minutes, and keeps the change only if val_bpb (validation bits per byte, lower is better) goes down. In the upstream run in progress.png, 83 experiments ran, 15 were kept (the baseline and 14 changes), and val_bpb fell from 0.9979 to about 0.977. The human stops editing Python and edits the agent's instructions in program.md instead.

What is autoresearch for?

It turns small-scale LLM research into a loop that an agent can run alone, for example while you sleep. A researcher normally edits training code, runs it, compares the result, and decides what to try next. autoresearch gives that whole loop to the agent. The training code is a simplified single-GPU version of nanochat, Karpathy's full LLM training repository.

The table compares the same research work without and with autoresearch. The last row is the main change: the human's work moves from the code to the instructions. The README calls program.md “a super lightweight skill”.

What does each file do, and who edits it?

Three files matter, and each has one owner. Figure 2 puts them in three panels. The human edits program.md. The agent edits train.py. Nobody edits prepare.py during a run.

The solid arrow is an import: train.py takes the clock, the data loader, and the metric from prepare.py. The dashed arrow means that program.md guides the agent's edits. This split is what makes the score trustworthy. program.md forbids the agent to modify prepare.py, to install new packages, or to change the evaluation. It calls evaluate_bpb “the ground truth metric”. If the agent could edit the metric, a lower number could mean a weaker test, not a better model.

val_bpb is the average number of bits the model needs to encode one byte of the fixed validation text. Fewer bits mean the model predicts the text better. The README chooses bytes, not tokens, so that architectural changes are “fairly compared”.

Source: program.md “What you CAN do” and “What you CANNOT do”; prepare.py lines 30–45 and 344 (evaluate_bpb); README.md “How it works”.

How does one experiment go from idea to keep or discard?

The agent commits each idea before it runs it. It keeps the commit only if val_bpb goes down; otherwise it resets the branch. Step through Figure 3: the top row is the current stage, and the bottom row is the git branch. Each dot is a commit.

Source: program.md “The experiment loop” (steps 1–9, timeout, crashes, NEVER STOP). The three example ideas and their numbers are the example rows in program.md “Logging results”, not a real run.

Two details keep the loop running without a human. First, results.tsv stays untracked, so git reset never deletes the record of a failed idea. Second, program.md tells the agent to never stop and ask “should I keep going?”. A run that takes more than 10 minutes is killed and counts as a failure.

Inference

“The branch tip is the best version” holds only if one run measures the idea, not luck. The loop runs each idea once. The last kept change in progress.png only changes the random seed (42 → 137), so part of the small late gains may be run-to-run noise.

Why a fixed 5-minute budget, and what does it cost?

A fixed budget makes every run comparable, whatever the agent changes. The cost is fewer training tokens per run, and results that depend on your GPU. Training stops when the training time reaches TIME_BUDGET = 300 s. The first 10 steps do not count, so compilation time does not use up the budget (train.py lines 578–579 and 603).

Move the slider in Figure 4 to change the budget. A run takes the budget plus about 26 s for startup and evaluation. In the upstream example output, total_seconds 325.9 − training_seconds 300.1 = 25.8 s.

experiments per night = 8 h × 3600 s ÷ (budget + 25.8 s)

At 5 minutes: 28,800 ÷ 325.9 ≈ 88 experiments. The README says “approx 100”, because it counts the 5 training minutes only (12 per hour × 8 hours = 96).

Source: prepare.py line 31; program.md “Output format” (example: 300.1 s, 325.9 s, 499.6 M tokens on an H100); README.md “Design choices”. The token bar assumes the H100 rate 499.6 M ÷ 300.1 s ≈ 1.66 M tokens/s.

The README names the cost directly. The budget finds the best model for your platform in 5 minutes. As a result, your runs “become not comparable” to runs on other hardware.

Inference

A short budget rewards changes that help in the first few minutes of training. A change that only pays off after longer training will look worse here and be discarded. A longer budget reduces this bias, but Figure 4 shows its price: fewer ideas per night.

How do I run it?

You need one NVIDIA GPU (tested on an H100), Python 3.10 or newer, and uv, a Python project manager. First check the setup by hand:

uv sync              # install the dependencies
uv run prepare.py    # one time, ~2 min: download data shards, train the tokenizer
uv run train.py      # one manual experiment, ~5 min

Then start your coding agent in the repository. The README says to start it “and disable all permissions”, so that the loop does not stop at permission prompts. Prompt it with:

Hi have a look at program.md and let's kick off a new experiment! let's do the setup first.

The agent then follows the “Setup” section of program.md. It agrees on a run tag with you (for example mar5), creates the branch autoresearch/mar5, checks that the data exists in ~/.cache/autoresearch/, and creates results.tsv. After you confirm, the first run is always the unchanged baseline.

Source: README.md “Quick start” and “Running the agent”; program.md “Setup”.

What does it not do?

  • It needs one NVIDIA GPU. The README links community forks for macOS, Windows, and AMD.
  • It does not compare results across hardware: a 5-minute run on another GPU trains a different amount.
  • It does not check a kept result with a second run (see the Inference box in the experiment-loop section).
