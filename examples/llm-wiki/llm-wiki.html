LLM Wiki：讓 LLM 替你維護一套會累積的知識庫

結論

LLM Wiki 是 Andrej Karpathy 提出的個人知識庫做法：每加入一份資料，就讓 LLM（large language model，大型語言模型）讀懂它，並把重點整合進一組互相連結的 Markdown 頁面，也就是 wiki。一般的 RAG（retrieval-augmented generation，提問時才從原始文件檢索片段來回答）每次提問都要重新拼湊；LLM Wiki 把整合工作提前到加入資料時，之後持續更新，所以知識會累積。這個做法行得通，是因為維護 wiki 最繁瑣的記帳工作交給了不會厭倦的 LLM，人只負責挑資料、提問與判斷。

LLM Wiki 和一般 RAG 差在哪裡？為什麼說知識會「累積」？

差別在於整合發生的時間點。RAG 在提問時才檢索原始文件的片段並拼成答案，所以每個問題都從零開始。LLM Wiki 在加入資料時就讓 LLM 讀懂內容，寫進 wiki 並更新相關頁面。作者把這稱為「編譯一次，之後保持最新」。

圖 2 用三份來源示範兩種做法；請逐步按 ▶。原文的例子是一個需要綜合五份文件的問題，圖中為了畫得清楚，簡化為三份。橄欖色是原始來源，紫色是 wiki 的頁面。前三步是加入來源：左邊的索引只多了互不相連的片段；右邊的概念頁（concept page，整理同一個概念的 wiki 頁面）每一步都被改寫。第 3 步的來源 C 與 A 說法不同，wiki 會在頁面上標出這個矛盾。第 4 步提出需要綜合三份來源的問題：RAG 得當場找回三個片段來拼湊，wiki 則直接讀已經整合好的頁面。

來源：〈LLM Wiki〉§ The core idea（RAG 與 wiki 的對比、五份文件的例子）、§ Operations（答案歸檔）

這種累積適用於任何需要長期整理知識的情境。原文舉了 5 種，圖 3 逐一列出每一種放進什麼來源，以及 wiki 會長出什麼頁面。比較每張卡片的「wiki 會長出什麼」：不論來源是日記、論文還是會議紀錄，wiki 長出的都是彼此連結的頁面，而不是一疊摘要。

原始資料、wiki、schema 三層各自負責什麼？誰能修改哪一層？

三層的分工是「原始資料只讀、wiki 由 LLM 寫、schema 由人和 LLM 一起修訂」。schema 是一份給 LLM 的規則文件，例如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md。

原文說 wiki「夾在你與原始來源之間」。圖 4 把三層畫成一個資料夾的上中下三層：schema、wiki、原始來源（raw sources），左邊是 LLM，右邊是你，箭頭是資訊流動的方向。請看中間那一層：指向它的箭頭只有一條，來自 LLM；你的箭頭只指向上下兩層。作者說，有了 schema，LLM 才會是「守紀律的 wiki 維護者」，而不是一般的聊天機器人。

作者也說，wiki 本身就是一個由 Markdown 檔案組成的 git repo，所以版本紀錄與分支都不用另外做。他用一句話描述三者的關係：「Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.」Obsidian 是一套以 Markdown 檔案為基礎的筆記軟體。作者一邊開著 LLM 代理，一邊用 Obsidian 即時瀏覽 LLM 改過的頁面。

來源：〈LLM Wiki〉§ Architecture、§ The core idea、§ Tips and tricks（git repo、raw/assets/）、§ Note（不規定目錄結構）

Ingest、Query、Lint 三種操作各自怎麼進行？

三種操作分別負責「加入資料」「回答問題」「定期健檢」，而且三種都會讓 wiki 變得更完整。

操作你做什麼LLM 做什麼對 wiki 的影響
Ingest（加入資料）把新來源放進原始資料，請 LLM 處理讀來源、和你討論重點、寫摘要頁、更新索引與相關的實體頁和概念頁、在日誌加一筆紀錄一份來源可能更新 10–15 頁
Query（提問）對 wiki 提問找出相關頁面、閱讀後附引用回答；形式可以是頁面、比較表、投影片或圖表好的答案歸檔成新頁面
Lint（健檢）定期請 LLM 檢查找出頁面間的矛盾、被新來源取代的舊說法、沒有任何連入的孤兒頁、缺少專頁的重要概念、缺少的交叉連結修正不一致，並建議下一步要查的問題與來源

來源：〈LLM Wiki〉§ Operations

Query 那一列最容易被忽略。作者強調，你要求的比較或分析不應該消失在聊天紀錄裡；把它歸檔成新頁面，你的探索就會和加入的資料一樣累積下來（圖 2 第 5 步）。至於 Ingest 要一次一份還是批次處理，作者偏好一次一份並全程參與，但他也說這取決於個人習慣，習慣確定後寫進 schema 即可。

index.md 和 log.md 有什麼不同？為什麼不用 embedding 檢索也能運作？

index.md 依內容分類，回答「wiki 裡有什麼」；log.md 依時間排序，回答「最近做了什麼」。在中等規模下，LLM 先讀 index.md 找到相關頁面，再進入頁面細讀，因此不需要 embedding（把文字轉成向量，用來做相似度檢索）的基礎設施。

圖 5 打開這兩個檔案，比較它們的排列方式：左邊依類別分組，右邊每一筆都以日期開頭、只往下追加。

作者說，這種做法在約 100 份來源、數百個頁面的規模下「出乎意料地好用」。規模再大時，就需要真正的搜尋工具。他舉的例子是 qmd：一個在本機執行的 Markdown 搜尋引擎，結合 BM25（依關鍵字出現頻率排序的傳統檢索方法）與向量檢索，並用 LLM 重新排序結果。

log.md 的每一筆若用固定的開頭格式，就能用一般的 Unix 工具解析。例如下面的指令會列出最近 5 筆紀錄：

## [2026-04-02] ingest | Article Title      ← log.md 中一筆紀錄的開頭
grep "^## \[" log.md | tail -5             ← 列出最近 5 筆

來源：〈LLM Wiki〉§ Indexing and logging、§ Optional: CLI tools

這個做法為什麼行得通？人和 LLM 怎麼分工？

因為知識庫最累人的部分是記帳，不是閱讀或思考，而記帳正好是 LLM 不會厭倦的工作。作者觀察到，人會放棄 wiki，是因為維護負擔成長得比 wiki 的價值還快；更新交叉連結、讓摘要保持最新、標出新舊資料的矛盾，都是這類負擔。LLM 不會忘記更新某個連結，一次可以改動 15 個檔案，所以維護成本趨近於零，wiki 才能一直保持在被維護的狀態。

人負責LLM 負責
挑選來源、決定分析方向、提出好問題、思考這些內容代表什麼其餘全部：摘要、交叉連結、歸檔、記帳

作者也把這個想法連到 Vannevar Bush 在 1945 年提出的 Memex：一個私人、由本人策劃、文件之間有聯想連結的知識庫。作者認為 Bush 沒有解決的問題是「誰來維護」，而 LLM 補上了這一塊。

來源：〈LLM Wiki〉§ Why this works、§ The core idea

限制與原文沒有說明的部分

  • 原文刻意寫得抽象：它只描述模式，不規定目錄結構、頁面格式或工具；具體做法要和自己的 LLM 代理一起決定（§ Note）。
  • 原文沒有任何實測數據；「10–15 頁」「約 100 份來源」都是作者的經驗描述。
  • LLM 無法一次讀完含有內嵌圖片的 Markdown；作者的做法是先讀文字，再個別查看圖片（§ Tips and tricks）。

推論

因為 wiki 全部由 LLM 撰寫，某一頁的錯誤可能透過交叉連結擴散到其他頁面。原文的 Lint 健檢，以及作者親自閱讀摘要、檢查更新的習慣，可以視為對這個風險的緩解，但原文沒有直接討論這一點。
