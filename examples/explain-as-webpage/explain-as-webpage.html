explain-as-webpage: turn what you do not understand into one knowledge page

Conclusion

This repository provides one agent skill, explain-as-webpage. You give it a project, a document, or a topic, plus your questions. The agent then follows the 7 steps in SKILL.md and builds one self-contained HTML page in the Read the Docs style that opens offline. Only step 4 needs you: the agent lists the questions, the presentation tier, and the output path once, and it builds only after you answer. The rules are split into 1 main file and 5 reference files. Every session holds only the description (an estimated 400 tokens); calling the skill loads the main file (an estimated 3.7k tokens); the reference files load only at the step that needs them.

What problem does the skill solve, and what does it produce?

It solves "the agent finished, and I do not understand what it did". An agent wrote a package, used an algorithm, or left a long analysis report; you must judge or change it, but you cannot find the chain of causes in it. The skill is inspired by a post by Andrej Karpathy (a screenshot is in README.md). The third round of work (v3) extends it from projects to documents and topics: without a software project, an article, a PDF, or a topic becomes an equally readable page.

FormOne .html file per page in the Read the Docs look (sphinx_rtd_theme); no build step and no extra image or script folders
OfflineEvery figure is inline SVG, and the CSS and scripts are inside the file; the page loads no external resources
StructureThe conclusion first, then one spine through the page; every h2 is a question the reader would ask
LengthAbout 15 minutes of reading: at most about 1,800 words of prose, or about 3,500 CJK characters
LanguageEnglish or Traditional Chinese; if you do not say, the language you write in
Templateassets/template.html (254 lines) with a sidebar table of contents, an optional page tree, and a shared stepper component

Source: README.md § Inspiration, § What it produces; docs/specs/explain-as-webpage-v3.md §0; references/writing-rules.md § Length budget; CLAUDE.md § 架構 (architecture).

How do reading and citing change with the material?

Step 1 picks one of three modes from what you give. The mode decides how the agent reads the material, how each fact names its source, and the default output path.

ModeYou giveHow the agent reads itHow a fact names its source
projectA repository, a report, a code pathReads the filesFile path + section heading or line
documentA web article, a PDF, Markdown, pasted textGets the full text with curl or pdftotextThe material's heading or page
topicOnly a topic and questionsPrimary sources first, then searchSource + access date + grade

Source: SKILL.md § 1; references/sources-and-research.md §1.

The most important rule of document mode is "the full text, not a summary". The table shows a test from task T1 on the same two articles. A fetch tool that answers through a model, such as WebFetch, gives the model's summary; curl plus local tag stripping gives the original text.

MaterialWebFetchcurl + tag stripping
Paul Graham, "How to Do Great Work"Asked for the text word for word, it refused for copyright reasons and gave only a summary and short quotesFull text, 11,738 words, ending with the acknowledgements
Karpathy, "LLM Wiki" gistAll 9 headings correct, but the section lengths were guesses, about 2,170 words in totalFull text, 1,921 words, the ending matches the original

Source: tasks/plan.md § "T1（2026-10-03，Claude Code）" item 1.

In topic mode, you choose the research depth: light means about 5–10 sources; deep means at least two independent sources for every key claim, and the page says where sources disagree. Every source carries a grade and an access date: g1 Primary (papers, official documentation), g2 Authoritative (government agencies, professional societies), g3 Secondary (news, encyclopedias), g4 Emerging (one person's claim). A claim that only g4 sources support goes into an Emerging view box that names who makes it. The Starship page works this way: SpaceX flight reports are g1, NASA pages are g2, Wikipedia is g3, and Musk's guess about cost sits in an Emerging view box. Health, safety, law, and personal finance are high-risk topics: only g1–g2 sources, a reader's own national agencies first, a Caution box on the page, and no doses or individual advice.

Source: references/sources-and-research.md §7, §8, §9; examples/starship-reusability/starship-reusability.html § 來源 (sources).

How does it decide what a page looks like?

Two independent choices decide it. The page type decides Figure 1 (the spine of the page) and the section skeleton; the tier decides how interactive the page is. Step 2 picks the page type from what the material is:

Page typeThe material isFigure 1 (spine)
Mechanism (default)A technique, an algorithm, a physical or biological mechanismCausal chain
Package or architectureA code package: what it does and why it is built this wayMain flow of one unit of work through the modules
Code walkthroughOne file or module, usually a child pageCall flow through its main functions
ArgumentAn essay, an opinion piece, a way of thinkingArgument map
Roadmap or planA plan with stages, tasks, and checksRoadmap of stages; a page tree by default
Practical guideHow to prepare for or decide somethingDecision tree or grouped checklist
EvolutionAn idea that changed through named stagesEvolution of stages

Source: references/page-types.md, the table at the top.

Step 3 picks the tier: the lowest tier that answers every question, decided question by question (Figure 2). Only a question about a process gets an animation; the rest of the page stays static. Which file is read when, and why are the rules split this way?

An agent platform keeps only each skill's description (the description at the top of SKILL.md) in every session; the body loads only when the skill is called. So the longer the rules, the more every call costs. This repository keeps only the process and the criteria in SKILL.md (at most about 130 lines) and moves the details into reference files, which the agent reads at the step that needs them (Figure 3).

The unit is tokens because this section asks about loading cost, and a model's context and its price are counted in tokens; file size is only a proxy. Source: estimates from claude --plugin-dir . plugin details sphinx-style-notes-maker (about 403 tokens always on, about 3.7k tokens per call). For the reference files and the template, each file was wrapped as its own test skill (3 lines of frontmatter added) and estimated with the same command. When each file is read: SKILL.md steps 1, 2, 4, 5 and the start of § Process.

Add up the estimates. A first build in project mode reads SKILL.md, page-types.md, writing-rules.md, svg-recipes.md, and the template: 3.7k + 3.2k + 3.7k + 6.4k + 6.2k ≈ 23.2k tokens. Document or topic mode adds sources-and-research.md, about 28.9k tokens. All files together are about 31.8k tokens. File size does not stand in for tokens: writing-rules.md is only 9.8 KB, but its estimate is about 3.7k, the same as the 11.8 KB SKILL.md, because the files differ in their share of CJK text and code. CLAUDE.md also states the rule: when the rules change, SKILL.md stays at about 130 lines or fewer, and the details go into the reference files.

Source: the estimates in Figure 3 (the sums are computed on this page); file sizes measured with wc -c; CLAUDE.md § 架構 (architecture), last paragraph.

Inference

The cost of this split is that the rules are spread over 6 files that refer to each other by section number (for example sources-and-research.md §7). When a section of one file changes, the files that refer to it must be checked too.

How does a page grow into a page tree with follow-up questions?

When you ask more about an existing page, the agent first reads extending-pages.md and decides where each new question goes (Figure 4). The principle: every page keeps its own length budget, so the hub page does not keep growing.

Source: references/extending-pages.md §2.

A child page answers 3–5 related questions, not one question per page. If a topic would pass about 6 child pages, the agent proposes a new topic instead. Every page carries the same page tree in its sidebar and marks the page you are on. Step 6 then runs three more commands: the page tree is the same on every page, every page marks itself, and every linked file exists. This repository's examples/autoresearch/ grew this way: after the hub page, the two code walkthrough pages autoresearch--train-py.html and autoresearch--prepare-py.html were added as follow-up questions. Long material or a plan can also get a page tree at the first build, with one child page per stage (§6).

Source: references/extending-pages.md §2, §4, §5, §6; README.md § Examples.

Status and limits

  • The material modes of round 3 were tested in Claude Code with 8 cases (tasks/todo.md, phases 1–4). The test in Codex (task T16) has not run yet, and the plugin manifests are still at version 0.2.0.
  • No video: the highest tier is an in-browser step animation. A video URL is not accepted as material either, because the agent cannot watch it.
  • A page that needs a login (for example a post on X) needs a web-reading helper skill, or the user saves it as a PDF.
  • All token numbers in Figure 3 are estimates from claude plugin details and may differ from actual use; the estimates for the reference files include the 3 lines of frontmatter added for the test skill.
