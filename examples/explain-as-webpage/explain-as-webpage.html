explain-as-webpage: turn what you do not understand into one knowledge page

Conclusion

This repository is the plugin explain-as-webpage. It provides two agent skills (a skill is a set of instructions and files for an agent): explainer-page runs the process and writes the page, and explainer-figure draws the figures. You give it a project, a document, or a topic, plus your questions. The agent then follows 7 steps and builds one self-contained HTML page in the Read the Docs style that opens offline. Only step 4 needs you: the agent lists the questions, the tier, the planned figures of each page, and the output path once, and it builds only after you answer. Every session holds only the description (an estimated 390 tokens); the other rules sit in 8 reference files and the template, and load at the step that needs them.

The commands in step 6 check four things: no template placeholder is left, the page loads no external resources, the file is about 150 KB or smaller, and in topic mode every source has a grade and an access date. Then headless Chrome takes screenshots at 1280 px and 390 px; the 390 px check puts the page in an iframe, because a Chrome window is at least 500 px wide. A page with figures is then checked figure by figure with explainer-figure: no label crosses a line, every arrow ends at a box edge, and every text colour has a contrast of at least 4.5:1 on every background (WCAG AA, the lowest level of the Web Content Accessibility Guidelines).

Source: SKILL.md § 6. Self-check; explainer-figure/SKILL.md § Self-check.

What problem does the skill solve, and what does it produce?

It solves "the agent finished, and I do not understand what it did". An agent wrote a package, used an algorithm, or left a long analysis report; you must judge or change it, but you cannot find the chain of causes in it. The skill is inspired by a post by Andrej Karpathy (a screenshot is in README.md). It also works without a software project: an article, a PDF, or a topic becomes an equally readable page.

FormOne .html file per page in the Read the Docs look (sphinx_rtd_theme); no build step and no extra image or script folders
OfflineFigures are inline SVG or HTML cards, and only the icons the page uses are copied in; the CSS and scripts are inside the file, and the page loads no external resources
StructureThe conclusion first, then one spine through the page; every h2 is a question the reader would ask
LengthAbout 15 minutes of reading: at most about 1,800 words of prose, or about 3,500 CJK characters
LanguageEnglish or Traditional Chinese; if you do not say, the language you write in
Templateassets/template.html (297 lines) with a sidebar table of contents, an optional page tree, a shared stepper component, and the styles for cards, concept colours, pictorial figures, and icons

Source: README.md § Inspiration, § What it produces; references/writing-rules.md § Length budget; CLAUDE.md § 架構 (architecture); template lines counted with wc -l.

How do reading and citing change with the material?

Step 1 picks one of three modes from what you give. The mode decides how the agent reads the material, how each fact names its source, and the default output path.

ModeYou giveHow the agent reads itHow a fact names its source
projectA repository, a report, a code pathReads the filesFile path + section heading or line
documentA web article, a PDF, Markdown, pasted textGets the full text with curl or pdftotextThe material's heading or page
topicOnly a topic and questionsPrimary sources first, then searchSource + access date + grade

Source: SKILL.md § 1; references/sources-and-research.md §1.

The most important rule of document mode is "the full text, not a summary". A fetch tool that answers through a model, such as WebFetch, returns the model's summary and may refuse to reproduce a long article. So the skill uses it only for a quick outline, or when curl is blocked; a page that rests on a summary says so in the report. The table shows a test on the same two articles.

MaterialWebFetchcurl + tag stripping
Paul Graham, "How to Do Great Work"Asked for the text word for word, it refused for copyright reasons and gave only a summary and short quotesFull text, 11,738 words, ending with the acknowledgements
Karpathy, "LLM Wiki" gistAll 9 headings correct, but the section lengths were guesses, about 2,170 words in totalFull text, 1,921 words, the ending matches the original

Source: references/sources-and-research.md §2; the numbers in the table are the author's own test (2026-10-03).

The agent does not try to get around what it cannot read, such as a video or a paper behind a paywall or a login. It says why in the confirmation and proposes ways to get the text, the highest fidelity first: the full text you can access, a transcript, or notes from a tool such as NotebookLM. A page built from such notes gets a Note box under the conclusion, grades the notes g3, and keeps the tool's own opinions apart from the original content.

In topic mode, you choose light or deep research. Every source carries a grade and an access date, from g1 Primary (papers, official documentation) to g4 Emerging (one person's claim); a claim that only g4 sources support goes into an Emerging view box. Health, safety, law, and personal finance are high-risk topics: only g1–g2 sources, a Caution box on the page, and no doses or individual advice.

Source: references/sources-and-research.md §2 Material you cannot read, §7, §8, §9.

How does it decide what a page looks like?

Three independent choices decide it. The page type decides Figure 1 (the spine of the page) and the section skeleton; the tier decides how interactive the page is; the figure type is chosen figure by figure (next section). Step 2 picks the page type from what the material is:

Page typeThe material isFigure 1 (spine)
Mechanism (default)A technique, an algorithm, a physical or biological mechanismCausal chain
Package or architectureA code package: what it does and why it is built this wayMain flow of one unit of work through the modules
Code walkthroughOne file or module, usually a child pageCall flow through its main functions
ArgumentAn essay, an opinion piece, a way of thinkingArgument map
Roadmap or planA plan with stages, tasks, and checksRoadmap of stages; a page tree by default
Practical guideHow to prepare for or decide somethingDecision tree or grouped checklist
EvolutionAn idea that changed through named stagesEvolution of stages

Source: references/page-types.md, the table at the top.

Step 3 picks the tier: the lowest tier that answers every question, decided question by question (Figure 2). Only a question about a process gets an animation; the rest of the page stays static. This page is a package page at L0: Figure 1 is the main flow of a request through the steps, and no question needs interaction.

Source: SKILL.md § 3 (tier table, relative cost) and Red Flags.

What can a figure be besides boxes and arrows?

Step 2 writes one figure brief per figure: the question it answers, its type, the facts it shows with their units, and its concept colours. explainer-figure checks each brief against its table of figure types and picks one of the four types in Figure 3. Compare the "Answers" field of the cards to see which type a figure needs.

Source: explainer-figure/SKILL.md § Choosing the figure type; the captions of examples/starship-reusability/ and examples/llm-wiki/.

Two rules make the figures of a page read as one set. The first is concept colours: a key concept keeps one colour on every figure, and a chip in the text matches the word to the colour, as explainer-page and explainer-figure do on this page. Red, green, orange, and blue stay reserved for the problem, the fix, the consequence, and neutral parts; a concept never uses them, because the reader would read a red concept as a problem. The second is icons: the skill bundles a subset of 106 icons from the Lucide library, and a page copies in only the icons it uses, with the license notice. An icon sits next to a label that names the same thing; it never replaces the label.

Source: explainer-figure/references/svg-recipes.md § Colour meaning; explainer-figure/references/icons.md.

Which file is read when, and why are there two skills?

An agent platform keeps only each skill's description (the description at the top of SKILL.md) in every session; the body loads only when the skill is called. So both SKILL.md files keep only the process and the criteria (each at most about 130 lines), and the details sit in reference files that the agent reads at the step that needs them (Figure 4). The drawing rules are a skill of their own because the work splits: explainer-page decides what each figure must show, and explainer-figure decides how to draw it. explainer-figure is not triggered on its own; explainer-page reads it by a relative path, so the two skill folders must sit side by side.

The unit is tokens because this section asks about loading cost, and a model's context and its price are counted in tokens; file size is only a proxy. Source: estimates from claude --plugin-dir . plugin details explain-as-webpage (about 529 tokens always on in total; about 4.2k for explainer-page and 2.5k for explainer-figure per call). Each reference file and the template was wrapped as its own test skill (3 lines of frontmatter added) and estimated with the same command (2026-10-07). That Codex lists explainer-figure and Claude Code does not load its description is the author's own test; the split and the trigger settings: the frontmatter and § Overview of explainer-figure/SKILL.md; the line limit: CLAUDE.md § 架構 (architecture), last paragraph.

Add up the estimates. A first build in project mode without cards, pictorial figures, or icons reads the explainer-page SKILL.md, page-types.md, writing-rules.md, and the template, plus the explainer-figure SKILL.md and svg-recipes.md: 4.2k + 3.9k + 4.9k + 7.9k + 2.5k + 7.0k ≈ 30.4k tokens. With all three new figure types, add cards.md, pictorial.md, and icons.md: about 41.1k. All files together are about 52.2k.

Inference

The cost of this split is that the rules are spread over 2 SKILL.md files, 8 reference files, and the template, which refer to each other by section number and relative path (for example ../explainer-figure/SKILL.md § Figure brief). When a section of one file changes, the files that refer to it must be checked too.

How does a page grow into a page tree with follow-up questions?

When you ask more about an existing page, the agent first reads extending-pages.md and decides where each new question goes (Figure 5). The principle: every page keeps its own length budget, so the hub page does not keep growing.

Source: references/extending-pages.md §2.

A child page answers 3–5 related questions, not one question per page. If a topic would pass about 6 child pages, the agent proposes a new topic instead. Every page carries the same page tree in its sidebar and marks the page you are on; step 6 also checks that the tree is the same on every page and that every linked file exists. This repository's examples/autoresearch/ grew this way: after the hub page, the two code walkthrough pages were added as follow-up questions. Long material or a plan can also get a page tree at the first build, with one child page per stage.

Source: references/extending-pages.md §2, §4, §5, §6; README.md § Examples.
